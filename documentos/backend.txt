===============================================================================
BACKEND — Sistema PWA de Evaluación Basada en Riesgo (EBR/BPM)
Bitácora de avance de implementación (contrato: documentos/API_CONTRACTS.md)
===============================================================================
Patrón seguido: el de apps/backend en el proyecto UNJ (Escritorio/UNJ_FORMS
REMOTO) -> <modulo>.model.ts (Prisma) -> <modulo>.service.ts (lógica) ->
<modulo>.controller.ts (HTTP) -> <modulo>.router.ts (rutas), con middlewares
compartidos vía alias "#backend/middlewares" y errores centralizados en
handlers/errorHandler.ts.

-------------------------------------------------------------------------------
⚠️  PASOS MANUALES REQUERIDOS ANTES DE CORRER EL BACKEND (no tengo terminal
    en esta máquina, solo acceso a archivos vía el conector Filesystem)
-------------------------------------------------------------------------------
1. pnpm install
   (agregué "tsx", "nodemon", "@types/bcrypt" a apps/backend/package.json y
   "zod" como dependencia runtime; también agregué scripts "build" a
   packages/db y packages/shared)

2. pnpm build:packages
   (= pnpm build:db && pnpm build:shared)
   IMPRESCINDIBLE: @reto/db y @reto/shared se consumen desde su carpeta
   dist/ (ver "exports" en sus package.json), NO desde src/. Cualquier
   cambio en packages/db/src o packages/shared/src (incluido el que hice
   hoy) no tiene efecto hasta reconstruir. Repetir este paso cada vez que
   se toquen esos paquetes.

3. pnpm --filter @reto/backend seed:roles
   Crea (upsert) los 5 roles del enum UserRole (ADMIN, ADMIN_EMPRESA,
   USUARIO_DELEGADO, COORDINADOR, TECNICO_EVALUADOR). Sin esto no hay
   roleId válidos para /users/register.

3b. pnpm --filter @reto/backend seed:risk-rules  (NUEVO, sesión 3)
   Crea las 3 reglas por defecto de la matriz de riesgo. Sin esto,
   POST /evaluations/:id/finish fallará con 500 INTERNAL_ERROR ("No hay
   una RiskFrequencyRule que cubra el puntaje calculado") porque el motor
   de riesgo no tiene con qué mapear el puntaje a nivel/frecuencia.

4. pnpm dev:backend  (o: pnpm --filter @reto/backend dev)
   Levanta con tsx+nodemon en http://localhost:3000, API bajo
   http://localhost:3000/api/v1

NOTA (sesión 2): agregué el módulo attachments, que usa `multer` para
`multipart/form-data`. Esa dependencia se sumó recién a package.json, así
 que el paso 1 (pnpm install) hay que volver a correrlo si ya lo habías
 hecho antes de esta sesión. Sin `multer` instalado, cualquier ruta que use
 `uploadSingleFile` (POST /attachments, POST /bpm-requests/:id/attachments)
 fallará al arrancar ("Cannot find module 'multer'").

Revisar .env / env-example.txt: agregué PORT, CORS_ORIGIN y los secretos
JWT_ACCESS_SECRET / JWT_REFRESH_SECRET / *_EXPIRES_IN (valores dummy de
desarrollo, cambiar antes de producción).

-------------------------------------------------------------------------------
CAMBIO EN PAQUETE COMPARTIDO (no era parte de un módulo, pero era bloqueante)
-------------------------------------------------------------------------------
packages/db/src/index.ts exportaba `Prisma` solo como *type*
("export type {Prisma}"). Eso rompe en runtime cualquier uso de las clases
de error de Prisma (ej. `Prisma.PrismaClientKnownRequestError`, usado en
errorHandler.ts para distinguir P2002/P2025). Se cambió a
`export { Prisma } from './generated/prisma/client.js'` (namespace, exporta
valor + tipo). Requiere rebuild (paso 2 arriba).

  seeder busca primero por una "clave natural" (cedula, rnc, name,

  otra con no conformidades, para que el motor de riesgo dé niveles

SESIÓN 6 — FIX: pnpm seed daba ECONNREFUSED aunque Postgres sí estaba arriba
===============================================================================
Síntoma: `pnpm seed` llegaba a ejecutar la primera query (roles.seeder.ts) y
fallaba con `PrismaClientKnownRequestError ... code: 'ECONNREFUSED'`, a pesar
de que el contenedor docker-pg (docker-pg/docker-compose.yml, puerto host
5433 -> 5432 del contenedor) estaba corriendo.

CAUSA RAÍZ (no era Postgres, era orden de carga de módulos ESM):
`packages/db/src/client.ts` lee `process.env.DATABASE_URL` en el momento en
que el módulo se evalúa (ahí mismo construye `new PrismaPg({ connectionString
: process.env.DATABASE_URL! })`). El `lib/seeders/index.ts` original importaba
todos los *.seeder.ts (y por lo tanto `@reto/db`) con IMPORTS ESTATICOS, y
recién después llamaba (ni siquiera llamaba) a dotenv. En ESM los imports
estáticos de un archivo se resuelven y ejecutan ANTES que el cuerpo de ese
mismo archivo, así que aunque se hubiera puesto `dotenv.config()` al inicio
del archivo, `@reto/db` ya se habría evaluado antes con `DATABASE_URL`
indefinido. Con `connectionString: undefined`, el driver `pg` cae a sus
valores por defecto (`localhost:5432`) en vez del `5433` real del contenedor
-> nada escucha ahí -> ECONNREFUSED. `apps/backend/src/index.ts` YA evitaba
este problema para `app.js` usando `await import('./app.js')` (import
DINÁMICO) después de `dotenv.config()`; el orquestador de seeders no
seguía ese mismo patrón.

Además se encontró un segundo bug en el mismo archivo: `seedAll()` se
llamaba dos veces (una dentro del bloque `if (isMain)` y otra suelta al
final del archivo sin ninguna condición), así que cada seeder corría dos
veces en la misma ejecución (inofensivo gracias a la idempotencia, pero
redundante y más lento).

FIX aplicado — se separó en dos archivos:
[x] lib/seeders/seed-all.ts (NUEVO)
      Contiene el arreglo STEPS y `export async function seedAll()`
      (el mismo contenido de antes, sin el bloque de ejecución). Este
      archivo importa estáticamente cada *.seeder.ts como antes — eso es
      seguro AQUÍ porque `seed-all.ts` mismo solo se carga vía import
      dinámico desde index.ts, nunca de forma estática.
[x] lib/seeders/index.ts (REESCRITO, ahora mínimo)
      1. `import dotenv/path/url` (nada que dependa de @reto/db)
      2. `dotenv.config({ path: resolve(__dirname, '../../../../../.env') })`
         (5 niveles: seeders -> lib -> src -> backend -> apps -> raíz)
      3. `const { seedAll } = await import('./seed-all.js')` (DINÁMICO)
      4. `const { default: prisma } = await import('@reto/db')` (DINÁMICO,
         solo para el $disconnect() final)
      5. corre seedAll() UNA sola vez y hace exit(0)/exit(1) según resultado
      Exactamente el mismo patrón que ya usa apps/backend/src/index.ts para
      `app.js`, documentado con un comentario largo en el propio archivo

No se tocó ningún *.seeder.ts individual: todos ya usaban
