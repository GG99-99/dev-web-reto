11) Security validation during the same journey

This should be done as part of the same run.

Check A: another company cannot see the new establishment
- Log in as a different company user:
  - admin@lacteosdelnorte.do
  - or delegado@lacteosdelnorte.do
- Attempt to view the list of establishments
- Expected: they do not see Panadería La Vega, S.R.L.

Check B: unauthorized detail access is blocked
- Try to open the details of the new establishment via URL or direct navigation
- Expected: access denied / not allowed / no visible record

Check C: forbidden actions are hidden
- Another company should not see "Edit", "Assign", "Submit", or "Review" controls for this record
- Expected: those controls are absent or unusable

Check D: role mismatch is blocked
- A technician should not be able to access coordinator-level management screens
- A company user should not have access to platform-wide admin panels
- Expected: 403/redirect/hidden UI

---

Pass / fail criteria

The journey passes if:
- each role can access only their intended features
- the company can create and track its own establishment and BPM request
- coordinator can assign and review
- technician can complete and submit the evaluation
- risk assessment and reports are generated
- company can see final results
- other companies cannot see or access the wrong data

---

Best "whole-system" summary

The most meaningful end-to-end journey is:

New company user -> approved by admin -> creates establishment -> adds representative -> creates BPM request -> coordinator assigns technician -> technician performs field assessment -> coordinator reviews and closes -> company checks final status -> access control checked across roles

This one journey demonstrates most of the real business value of the system.
